# Local setup

## Requirements

Use Windows, Git, the .NET SDK specified by `server/global.json` (currently .NET 10), MySQL 8, and an existing compatible R575 client/native ZoneHost installation. The repository does not supply the game client or content databases. Follow the [upstream setup guide](https://github.com/AAEmu/AAEmu/wiki) for database bootstrap and client data requirements, and `server/Docs/` for protocol and configuration details.

## Build and check

Run from the repository root:

```powershell

dotnet restore server/AAEmu.slnx

dotnet run --project server/AAEmu.UnitTests/AAEmu.UnitTests.csproj --verbosity quiet -p:WarningLevel=0

dotnet build server/AAEmu.WorldServer/AAEmu.World/AAEmu.World.csproj -o artifacts/world

dotnet build server/AAEmu.Login/AAEmu.Login.csproj -o artifacts/login

```

Tests use Microsoft.Testing.Platform/TUnit. Integration tests require their own isolated test database and configuration; do not point them at the game database.

## Configure privately

Use the example local configuration files under the Login, Game and World projects as templates. Store real database credentials in ignored `Config.Local.json` files in the appropriate runtime folders. Configure matching Login/World shared secrets yourself; example values are placeholders. Bootstrap only your intended schemas and review migrations before applying them. Never apply a script containing `USE aaemu_game` blindly to a separately named test schema.

For the existing local setup, runtime folders are `F:\AAEmu-R575-compiled\Login` and `World`, and the client is `F:\AAEmu-R575-client`. Login listens on 1237, World on 1239, zone relay on 1240 and streaming on 1250. Bind local testing to the intended host; remote hosting requires separate network and account-security configuration.

World needs valid `GameContentRoot`, `ZoneGameDataRoot`, native ZoneHost executable, working directory and native DLL paths. See `server/AAEmu.WorldServer/AAEmu.World/Config.Local.json.example`. Native content is not generated by compiling the server.

## Zones and startup

Start the database, Login and World, then wait for startup readiness. Login/World TCP availability does not prove a destination zone is ready. Our local outdoor supervisor can start cold zones on demand, await `ZoneLoaded`, limit resident hosts and retire idle hosts. Current local settings are eight hosts, 120 seconds readiness timeout and 300 seconds idle unloading. Keep runtime settings private and match actual available memory.

The two initial test areas use zone keys 129/181. Native zone keys differ from SQLite `zones.id`; never substitute one for the other. `PreLoadTerrain` caches terrain data; it does not start every map or instance.

Before replacing running server assemblies, log all characters out and back up the database and affected runtime files. Build outputs from this repository require deployment; saving source does not update a running server.
